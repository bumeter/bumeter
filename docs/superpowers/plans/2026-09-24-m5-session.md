## Design decisions

- **Computed on open, not stored in the DB:** opening a session re-reads that session's log file (a few MB, about 50ms) and estimates the context composition in memory. No `call_composition` table is added, so the DB stays small. This differs from spec 6.1, and is recorded in the ledger.
- **Where the code lives:** the analysis part is in `tk-adapters/claude_code/composition.rs`, because it needs to know Claude's log format. The app calls this module directly. `tk-core` only provides the session's file path.
- **How the estimate works:** count the characters of each block and divide by 3.5, then **scale so the total equals the real `context`** of that call. On a compact, reset, and the summary is then counted into the "System" group.
- **Groups:** `system` (attachments, isMeta, compact summaries) · `skill` (results of the Skill tool) · `file_read` (Read/Grep/Glob, and Bash running cat/head/tail/sed) · `tool_io` (input and output of other tools) · `thinking` · `output` (answer text) · `user` (questions).

## Review Focus
1. A very long session (thousands of calls, a file of tens of MB) → the UI doesn't freeze and the chart stays readable.
2. Tool output containing malicious code or very long strings → shown as text and truncated.
3. A session with many compacts → each segment resets correctly.
4. A log missing `usage` or with broken lines → skipped, without failing the whole screen.
5. File paths in suggestions belong to the user's machine → shown only, never opened or executed.
