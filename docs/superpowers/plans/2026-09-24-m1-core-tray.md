# M1: Core + Tray — Implementation plan (condensed)

- Spec: `docs/superpowers/specs/2026-09-24-thongke-design.md` (sections 2, 4, 5, 7, 14)
- Goal: an app that runs in the background, reads Claude Code logs in realtime, shows 5h/7d quota in the tray, and sends notifications.
- Stack: Rust 1.94, Tauri 2.11 (plugins `tray-icon`, `notification`, `single-instance`), rusqlite 0.40 (bundled), notify 8, interprocess 2, clap 4.
- Follow TDD: for each task write the test first, then the code. Each task ends with a commit.

## General rules

- Tokens are always **deduplicated by `requestId`** (fallback `message.id`). If duplicate lines have different `usage`, take the largest value.
- Do not open any network port. The socket is in `data_dir/thongke/`, mode `0600`.
- Only one process (the host) writes to the DB, protected by a file lock. The DB runs in WAL mode.
- Historical data **must not generate notifications**. Only what happens after the host starts is notified.
- Test paths are overridden with the environment variables `TK_DATA_DIR` and `TK_CLAUDE_DIR`.

## Log findings used in the code

- Every `user` line (including lines containing a tool_result) has the `promptId` of the turn. `assistant` lines do not, so they must be assigned to the nearest `promptId` in the same file.
- A subagent's file is at `<project>/<session>/subagents/agent-*.jsonl`. Its first line has the `promptId` of the parent turn, so subagent tokens are counted toward the parent turn (marked `sidechain`).
- **Not counted as a prompt** when a line has one of these traits: `isSidechain`, `isMeta`, `isCompactSummary`, has a `toolUseResult`, content starting with `<`, or is `[Request interrupted…`.
- Skip the `<synthetic>` model. For lines with `error:"rate_limit"`, read `quotaLimits.{rateLimitType,resetsAt}`.
- The `cache_creation` part splits into 2: `cw1h = ephemeral_1h`, `cw5 = cache_creation_input_tokens − cw1h`.

## Review Focus (most error-prone in real use)

1. Claude is writing a line right as the app reads → that line must not be lost, nor counted twice (Task 4).
2. The app starts for the first time with hundreds of old sessions → **must not fire notifications** for historical data (Tasks 6, 10).
3. `limits.json` is old because Claude hasn't been opened in a while → no false alarms (Tasks 6, 7).
4. `tk daemon` and the app run together → only one side writes the DB, and the app takes over the host (Tasks 9, 10).
5. A client reads the DB (read-only) right as the host writes → no "database is locked" error: enable WAL and a 2-second `busy_timeout` (Tasks 3, 9).
